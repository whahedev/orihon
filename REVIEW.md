# Ревью библиотеки Orihon

**Версия:** 1.0.6 (+ 16 незакоммиченных/незарелизенных коммитов в ветке `fix/developer-experience-api`, из них 10 breaking)
**Объём:** 113 файлов TypeScript, 33 860 строк в `src/`; 81 файл тестов, 437 тест-кейсов, 10 720 строк
**Дата:** 28 августа 2026

Все находки ниже проверены по коду; отмеченные «(проверено)» дополнительно воспроизведены запуском против собранного `dist/`.

---

## Резюме

Кодовая база в очень хорошем состоянии по внутренней дисциплине: строгий TypeScript, ноль `TODO`/`FIXME`/`HACK` на 34 тысячи строк, ноль `console.*`, десять `any` на весь проект, осмысленная обработка ошибок в каждом из 58 `catch`. Явные единицы измерения в API (`durationMs`, `clusterRadiusPixels`) с активными guard'ами против старых имён и именованные координаты (`latLng` / `lngLat`) убирают целые классы типовых ошибок — этого нет ни у Leaflet, ни у OpenLayers. CI гоняет Node 22 и 24, три браузерных движка, тесты на утечки и проверку документации.

Основные риски лежат не в качестве кода, а в трёх местах: **заявленный размер бандла не соответствует фактическому**, **отсутствует восстановление после потери GPU-контекста**, и **React-обвязка построена на предположениях, которые React не выполняет**. Плюс `ObjectManager` вырос в god-класс на 4180 строк, а покрытие тестами нигде не измеряется — вместе это означает, что оценить реальный риск изменений в самой сложной части движка сейчас нечем.

Приоритеты: P0 — исправить до следующего релиза, P1 — до 2.0, P2 — в рабочем порядке.

## Что сделано хорошо

- **Три уровня входа (`core` / `standard` / `advanced`) с бюджетами размера, проверяемыми в CI.** Дисциплина есть, инфраструктура есть — только цифры в README разошлись с реальностью (см. P0-1).
- **Явные единицы в публичном API.** `zoomAnimationDurationMs`, `clusterRadiusPixels`, `getRadiusMeters()` / `getRadiusMapUnits()`, плюс `rejectLegacyUnit()` (`src/units.ts:9`), который бросает понятную ошибку на старое имя. Редкая для GIS-библиотек аккуратность.
- **Именованные координаты.** `latLng(lat, lng)` / `lngLat(lng, lat)` вместо анонимного массива — классический баг «перепутанный порядок координат» становится невозможен на уровне типов.
- **Безопасный путь по умолчанию для попапов.** Строковый контент идёт через `textContent` (`src/overlays/div-overlay.ts:217`), HTML требует явного блока через санитайзер. Правильная архитектура: небезопасное поведение нужно запросить осознанно.
- **Явный жизненный цикл.** `onAdd` / `onRemove` / `detach` / `destroy` на всех уровнях; GL-слои корректно зовут `WEBGL_lose_context.loseContext()` при разрушении (`src/layers/webgl-point-layer.ts:202`, `webgl-symbol-layer.ts:183`, `gpu-tile-layer.ts:742`).
- **Осмысленная обработка ошибок.** Ни одного «проглоченного» `catch {}` без комментария или fallback-а; в каждом либо восстановление, либо переброс, либо документированный отказ от фичи.
- **CHANGELOG с явными breaking-записями.** Раздел `Unreleased` описывает каждое ломающее изменение с миграцией — редкость.
- **Транзакционный `addLayer` / `addControl`** (`src/map.ts:777`, `:861`): при исключении в `onAdd` слой откатывается из набора. Хороший паттерн.

### 2. `tileLayer()` создаёт новый WebGL-контекст на каждый вызов и не освобождает его

> **Исправлено.** Проба мемоизирована на документ и освобождает контекст через `WEBGL_lose_context`; заодно сначала пробуется `webgl2`, как и в реальном слое.

`src/layers/tile-layer.ts:720-728`, вызывается из `tileLayer()` (`:695-696`):

```ts
function webglContextAvailable(): boolean {
  if (typeof document === "undefined") return false;
  try {
    const canvas = document.createElement("canvas");
    return Boolean(canvas.getContext("webgl") || canvas.getContext("experimental-webgl"));
  } catch { return false; }
}
```

Результат не мемоизируется, канвас не освобождается через `WEBGL_lose_context`. Браузеры держат жёсткий лимит живых WebGL-контекстов (Chrome — порядка 16); при превышении самые старые **принудительно теряются**.

**Сценарий отказа:** приложение с переключателем базовых слоёв создаёт `tileLayer()` при каждом переключении. После ~16 переключений браузер начинает убивать контексты — и первыми под нож идут контексты реально отрисовывающих слоёв (`webglPointLayer`, `heatLayer`), потому что пробные канвасы создаются последними. Карта частично чернеет без единой ошибки в консоли. То же самое воспроизводится с несколькими картами на странице или мини-картой.

**Фикс** (несколько строк): один раз посчитать в модульной переменной и сразу отпустить пробный контекст —

```ts
let webglProbe: boolean | null = null;
function webglContextAvailable(): boolean {
  if (webglProbe !== null) return webglProbe;
  if (typeof document === "undefined") return (webglProbe = false);
  try {
    const gl = document.createElement("canvas").getContext("webgl");
    gl?.getExtension("WEBGL_lose_context")?.loseContext();
    webglProbe = Boolean(gl);
  } catch { webglProbe = false; }
  return webglProbe;
}
```

Заодно: проба запрашивает `webgl`, а `gpu-tile-layer.ts:525` предпочитает `webgl2` — стоит согласовать.

### 3. Нет обработки потери GPU-контекста

По всему `src/` — ноль вхождений `webglcontextlost`, `webglcontextrestored`, `isContextLost`, `device.lost`, `uncapturederror`.

Затронуты: `src/layers/gpu-tile-layer.ts:525`, `src/layers/webgl-point-layer.ts:174`, `src/layers/webgl-symbol-layer.ts:159`, `src/layers/webgl-path-batch.ts:190`.

**Сценарий отказа:** пользователь сворачивает вкладку на несколько минут / у него срабатывает сброс драйвера GPU (TDR в Windows — штатное событие) / другая вкладка исчерпала лимит контекстов. Браузер отправляет `webglcontextlost`, все GL-ресурсы становятся невалидными. Orihon об этом не узнаёт: следующий `render()` пишет в мёртвый контекст, слой навсегда остаётся пустым, ошибок в консоли нет, восстановление возможно только через перезагрузку страницы.

Для движка, чьё позиционирование — «100 000+ объектов на GPU», это самый заметный для конечного пользователя класс отказов. Минимум: слушать `webglcontextlost` (с `preventDefault()`, иначе браузер не пришлёт `webglcontextrestored`), помечать слой как невалидный, по `webglcontextrestored` пересобирать программы/текстуры/буферы из уже имеющегося пака данных. Для WebGPU — подписка на `device.lost`.

### 4. `setView()` отменяет анимацию до проверки на no-op

> **Исправлено.** `stop()` вызывается только когда вид действительно меняется. Покрыто `test/camera-animation.test.js`.

`src/map.ts:920-923`:

```ts
setView(center, zoom = this.zoom, options?) {
  if (this._destroyed) return this;
  const settle = options?.settle !== false;
  if (settle) this.stop();          // <- отмена до проверки
  const nextCenter = latLng(center);
  ...
  if (!zoomChanged && !centerChanged) { ... return this; }
```

`map.setView(map.getCenter(), map.getZoom())` — логически пустая операция — убивает идущий `flyTo` и инерцию. (Проверено: `flyTo` с `durationMs: 400`, через 100 мс вызов `setView(getCenter(), getZoom())` — анимация не доходит до цели.)

Само по себе это мелочь. Проблемой это становится в связке с React-обвязкой (`src/react/map.ts:49-51`):

```ts
useLayoutEffect(() => { map?.setView(center, zoom); }, [map, center, zoom]);
```

`center` — объект. Типовое использование `<Map center={{ lat, lng }} zoom={z} />` создаёт новый литерал на каждый рендер, эффект срабатывает каждый раз, и **любой ререндер родительского компонента отменяет анимацию камеры**. `map.flyTo(...)`, вызванный из соседнего обработчика, не доживает до конца, если в этот момент что-то обновило состояние выше по дереву.

**Фикс:** перенести `this.stop()` за проверку `!zoomChanged && !centerChanged` (одна строка). React-часть — см. P1-8.

### 5. Прогресс анимации не ограничен снизу

> **Исправлено.** `Math.min(1, Math.max(0, …))` в обоих циклах; регрессионный тест подаёт кадр с временем раньше старта.

`src/map.ts:578` (`#animateView`) и `:606` (`#startInertia`):

```ts
const progress = Math.min(1, (now - startTime) / duration);
```

`startTime` берётся из `performance.now()` в момент вызова, `now` — таймстемп `requestAnimationFrame`, то есть **время начала кадра**. Если `flyTo()` вызван из обработчика события, который сам выполняется внутри уже начавшегося кадра, `now` может оказаться меньше `startTime`. Тогда `progress < 0`, `ease(t) = 1 - (1-t)³` тоже отрицательна, и первый кадр анимации уводит камеру в противоположную сторону от цели с последующим клампом по `minZoom`.

Под jsdom (где часы rAF и `performance.now()` вообще разного происхождения) это воспроизводится в чистом виде: `flyTo(..., zoom: 8, durationMs: 400)` со старта на зуме 3 приводит камеру на зум 0 и там оставляет (проверено). В Chrome эффект мягче — один кадр рывка назад, — но он реален и заметен.

**Фикс:** `Math.min(1, Math.max(0, (now - startTime) / duration))` в обоих местах. Ещё чище — брать `startTime` из таймстемпа первого кадра, а не из `performance.now()`.

### 7. `Evented`: три дефекта в базовом классе событий

> **Исправлено.** Все три, плюс `emit` больше не собирает объект события, когда слушателей нет. Покрыто `test/events-robustness.test.js`.

Все три проверены запуском.

**7a. Ошибка в одном обработчике останавливает остальные.** `src/events.ts:85-86` — `for (const handler of [...list]) handler(event);` без изоляции. Первый бросивший обработчик прерывает цикл, исключение всплывает наружу. Поскольку `emit` вызывается изнутри `#applyView()` и `#render()`, один сломанный пользовательский листенер на `move` ломает всю отрисовку карты, а не только себя. Leaflet ведёт себя так же, но там `emit` не вызывается из рендер-цикла на каждый кадр. Минимум — задокументировать контракт; лучше — `try/catch` вокруг вызова с ретрансляцией в `emit("error")`.

**7b. Циклические `addEventParent` → переполнение стека.** `src/events.ts:65-68` защищает только от прямого self-цикла (`parent !== this`). Цикл из двух узлов уходит в бесконечную рекурсию:

```js
a.addEventParent(b); b.addEventParent(a);
a.emit("x");  // RangeError: Maximum call stack size exceeded
```

Фикс: набор посещённых узлов, протаскиваемый через рекурсию распространения.

**7c. `off(type, handler)` не снимает подписку, оформленную через `once`.** `src/events.ts:37-43`: в `Set` кладётся обёртка, оригинальная функция недоступна, `off` по ней ничего не находит.

```js
const h = () => count++;
d.once("z", h);
d.off("z", h);
d.emit("z", {});   // h всё равно вызван
```

Фикс: `WeakMap<original, wrapper>` либо хранение оригинала на свойстве обёртки.

### 8. Явный `undefined` в опциях ломает конструкторы

> **Исправлено частично.** Добавлен `mergeOptions()` и применён в `Orihon` и `ObjectManager` (там, где падение воспроизводилось). Остальные ~37 мест со спредом дефолтов стоит перевести на него же.

`src/services/object-manager.ts:574` — `...options` поверх дефолтов, затем `:576` — валидация:

```js
objectManager({ clusterize: true, clusterRadiusPixels: undefined })
// RangeError: clusterRadiusPixels must be a finite non-negative number.
```

(Проверено.) `undefined` из `options` затирает дефолт, и `nonNegativeFinite` (`src/units.ts:2`) на нём падает. В React и TypeScript это происходит постоянно: `clusterRadiusPixels={props.radius}` при незаданном `radius`, `{...(cfg.radius && { clusterRadiusPixels: cfg.radius })}` с промахом, `exactOptionalPropertyTypes: false`.

Паттерн `{ ...defaults, ...options }` используется в **40 файлах** `src/` — вероятно, затронут не только `ObjectManager`. Показательно, что в `src/react/map.ts:31-33` эта проблема уже решена явной фильтрацией:

```ts
const definedOptions = Object.fromEntries(
  Object.entries(mapOptions).filter(([, value]) => value !== undefined)
);
```

То есть решение известно, но применено ровно в одном месте. Нужен общий хелпер `mergeOptions(defaults, options)`, отбрасывающий `undefined`, и его применение везде.

### 9. Разделяемый worker-пул никогда не освобождается

> **Исправлено.** Подсчёт ссылок: `acquireSharedGeometryWorkerPool()` в конструкторе `ObjectManager`, `releaseSharedGeometryWorkerPool()` в `destroy()`.

`src/services/geometry-worker.ts:600-605` — модульный синглтон `sharedGeometryWorkerPool`. `ObjectManager.destroy()` (`src/services/object-manager.ts:692`) оставляет его жить осознанно: «*The library-owned shared pool outlives individual managers*».

Проблема в том, что вместе с воркером остаётся живым и установленный в нём датасет координат — `Float64Array` на все объекты последнего менеджера (`_clusterDataset`, `geometry-worker.ts:117`). Публичного API для освобождения нет.

**Сценарий:** SPA, где карта — один из роутов. Пользователь заходит на карту с 500 000 объектов, уходит на другую страницу, компонент размонтируется, `ObjectManager.destroy()` отрабатывает — а поток и ~8 МБ координат остаются висеть до закрытия вкладки. При повторных заходах датасет переустанавливается, но старый воркер живёт всё это время.

**Фикс:** подсчёт ссылок (`acquire`/`release` вместо `get`) или экспортируемый `releaseSharedGeometryWorkerPool()` с очисткой датасета при нулевом счётчике.

### 10. React-обвязка предполагает референсную стабильность пропсов

`src/react/layers.ts`:

- `:42` — `useLayoutEffect(() => { layer.setLatLng(position); }, [layer, position])`
- `:58` — `layer.clearLayers().addData(data)` по зависимости `[layer, data]`
- `:60` — `useLayoutEffect(() => { if (style) layer.setStyle(style); }, [layer, style])`

`position`, `data`, `style` — объекты и функции. При обычном использовании (`<Marker position={{ lat, lng }} />`, `<GeoJSON data={features} style={f => ...} />`) их идентичность меняется на каждом рендере, и эффект срабатывает каждый раз. Для `Marker` это лишний `setLatLng` — терпимо. Для `GeoJSON` это **полный `clearLayers()` + `addData()`**, то есть пересборка всего слоя на каждый рендер родителя.

Ни мемоизации внутри, ни сравнения по значению, ни предупреждения в `docs/`. Пользователь узнаёт об этом по падению FPS.

**Варианты:** сравнивать по значению для позиции (дёшево, две координаты); для `data` — сравнивать по ссылке, но задокументировать требование `useMemo` заметно; для `style` — держать в `ref` и не пересоздавать слой.

### 11. React: часть пропсов молча игнорируется после монтирования

- `src/react/map.ts:35` — `initial.current` замораживает **все** опции карты кроме `center`, `zoom` и `locale`. Смена `minZoom`, `maxBounds`, `behaviors`, `keyboard` после монтирования не делает ничего.
- `src/react/layers.ts:52` — `initial.current` для `GeoJSON` замораживает `filter`, `pointToLayer`, `onEachFeature`.
- `src/react/layers.ts:30, 42` — из всего набора опций слоя синхронизируется только `opacity`. Смена `icon` у `Marker`, `zIndex` или `opacity`-подобных полей у `TileLayer` — тишина.

Молчаливый no-op на изменение пропса — худший из вариантов: ни эффекта, ни ошибки, ни предупреждения. Нужно либо синхронизировать, либо в dev-режиме предупреждать об игнорируемом изменении, либо документировать список «только при монтировании» прямо в типах (JSDoc на полях `MapProps` / `GeoJSONProps`).

### 12. Непоследовательный контракт после `destroy()`

> **Исправлено.** Всё, что присоединяется к карте, бросает `Orihon map was destroyed`; методы камеры и запросов остались инертными — это задокументировано в коде и покрыто существующим тестом.

Три разных поведения у одного объекта (проверено):

| Вызов после `map.destroy()` | Поведение |
| --- | --- |
| `map.setView(...)` | тихо возвращает `this` (`src/map.ts:921`) |
| `map.getPane("tile")` | возвращает `null` |
| `map.addLayer(...)` | бросает `Error: Orihon pane not found: tile` — внутреннюю ошибку, ничего не говорящую о причине |

Для сравнения, `ObjectManager` (`src/services/object-manager.ts:431`) делает это правильно: `assertAlive()` бросает явный `abortError("ObjectManager was destroyed")`.

Нужен единый контракт для `Orihon`: либо все мутирующие методы тихо игнорируются, либо все бросают понятную ошибку «map was destroyed». Второе лучше — молчаливое игнорирование прячет баги в приложении.

## P2 — в рабочем порядке

### 13. `ObjectManager` — god-класс на 4180 строк

Один класс держит ~100 приватных полей и ~150 методов и отвечает за: хранение объектов, пространственный индекс, DOM-маркеры, canvas-кластеры, WebGL-пак с инкрементальным патчингом стилей, тепловую карту, изолинии, лейблы с деклаттерингом, попапы объектов и кластеров, spiderfy, временной индекс, поиск, резолвинг стилей, координацию воркеров и greedy-кластеризацию с кэшем по зумам.

Это главный риск сопровождения проекта. Смежные признаки видны в самом коде: восемь `.bak`-снимков одного `cluster-layout.ts` рядом с исходником, поля вида `_webglSyncedZoom` / `_webglDataEpoch` / `_webglSyncedEpoch` / `_webglViewKey` — ручная инвалидация кэшей, размазанная по классу, где каждое новое условие рискует разъехаться с остальными.

**Рекомендация — эволюционная, не разовая:** ввести интерфейс `ObjectRenderer` (`sync(layout, viewport)`, `clear()`, `queryHit()`, `destroy()`) и вынести за него три реализации — `DomObjectRenderer`, `WebglObjectRenderer`, `CanvasClusterRenderer`. `ObjectManager` остаётся владельцем данных, индекса и выбора бэкенда. Делать по одному бэкенду за релиз, и **перед каждым шагом писать характеризационные тесты** на текущее поведение — иначе рефакторинг вслепую в такой связности опаснее, чем его отсутствие.

### 15. `latLngToLayerPoint` и `latLngToContainerPoint` идентичны

`src/map.ts:989` и `:993` — побайтно одинаковые реализации (проверено: возвращают равные значения). В Leaflet, откуда пришли оба имени, они различаются на смещение панели, и мигрирующий разработчик будет искать разницу там, где её нет.

### 16. `fitBounds` всегда даёт целый зум, игнорируя `zoomSnap`

`src/map.ts:1015` — `Math.floor(Math.min(zx, zy))`. При `zoomSnap: 0.25` (дефолт) `fitBounds` вернул 6 там, где дробный зум дал бы более плотную посадку (проверено). Дробный зум поддерживается везде остальное — исключение выглядит не намеренным. Либо снапить по `this.options.zoomSnap`, либо задокументировать как осознанное решение.

### 17. `emit` строит объект события даже когда слушателей нет

Замер на текущем `dist` (1 млн вызовов):

| --- | --- |
| `emit` с пятью обработчиками | 65 нс |
| `emit` **без единого обработчика** | 47 нс |

То есть ~70 % стоимости — аллокация и `delete` (последний ещё и переводит объект в словарный режим в V8). `Evented.listens()` в библиотеке есть (`src/events.ts:60`), но внутри не используется нигде.

Не критично по абсолютным цифрам, но `move` / `render` — горячий путь, и экономия бесплатная: ранний выход при отсутствии слушателей и родителей, плюс сборка события без `delete` (не класть `detail` вместо того чтобы удалять).

### 19. Санитайзер попапов построен на чёрном списке

`src/popup-content.ts:118-148`. Реализация аккуратная: нормализация схем от управляющих символов и пробелов перед проверкой (`java\nscript:` не проходит), снятие `on*` / `style` / `srcdoc` / `srcset` / `ping` / `formaction`, принудительный `rel="noopener noreferrer"` при `target="_blank"`, аллоу-лист схем URL. ### Десять падавших тестов: что оказалось внутри

Прогон всех 60 файлов тестов поимённо нашёл **10 падений** — все воспроизводятся на
чистом `HEAD`, то есть достались от коммитов `85ff597` («fix: land DX quick wins…») и
`ef5f569`. Разбор дал **три регрессии в коде** и **семь устаревших тестов**; починено
всё.

**Регрессии в коде (починен код):**

- **`Map.remove()` исчез молча.** `docs/API-DESIGN.md:24` называет его
  «documented ecosystem-compatible terminal alias of `Map.destroy()`»,
  `docs/API.md:351` перечисляет рядом с `destroy()`, react-тест на него опирался —
  а `85ff597` удалил метод без записи в CHANGELOG. Восстановлен, покрыт тестом.
- **`map.query()` читал приватное поле `#layers`.** После того как `ef5f569` сделал
  `map.layers` публичным `ReadonlySet`, метод остался на приватном поле, и
  `Orihon.prototype.query.call(...)` перестал работать. Переведён на публичный
  `this.layers`: хит-тест выражается через документированную поверхность
  (слои + порядок панелей), а не через внутреннее состояние.
- **Документация противоречила коду по словарю стилей.** `85ff597` добавил
  `rejectStyleAliases`, который **бросает** на `color` / `opacity` / `width`, но
  CHANGELOG, `docs/API.md` (два места) и `docs/API-DESIGN.md` продолжали утверждать,
  что это «remain aliases» и «canonical wins». Приведено в соответствие с кодом.
  Направление ветки (`rejectLegacyUnit`, `html`→`content`, снятие позиционных
  Easy-форм) однозначно говорит, что верен код, а не старая формулировка.

**Устаревшие тесты (починены тесты):**

- **Четыре теста под прежний контракт алиасов** — три в `object-manager-style`, один
  в `stage-eight` (`MarkerCollection`). Переписаны под текущий: канонический словарь
  работает, а каждое удалённое написание — и для точек, и для линий — проверяется на
  выброс ошибки с правильным текстом. Заодно исправлены ассерты, читавшие у батча
  путей старые имена `style.color/opacity/width` вместо
  `style.stroke/strokeOpacity/strokeWidth`.
- **Два теста в `stage-six` пострадали от слепого find-and-replace.** В них
  `marker()` вызывается с `fill` / `fillOpacity`, а читаются `options.color` /
  `options.opacity`. Marker сохраняет собственный словарь appearance
  (`color`, `strokeColor`, `size`, `strokeWidth`) — это документировано в
  `docs/API.md:96` и не менялось; переименование задело только стили точек
  ObjectManager и MarkerCollection. Входные параметры возвращены к `color` /
  `opacity`, добавлен комментарий про разделение словарей. Попутно всплыло, что
  `marker()` молча игнорирует незнакомые опции — отдельный случай той же проблемы,
  что и в React-биндинге (п. 11).
- **Два теста в `object-manager-lifecycle`** написаны до того, как `prepareLayout()`
  стал дожидаться отложенной сборки иерархии («then wait so `await prepareLayout()`
  means the hierarchy is settled»). Они делали `await prepareLayout()` **до** тика
  мок-таймера, то есть ждали промис, который по построению не мог разрешиться.
  Переписаны так, чтобы `destroy()` действительно происходил до диспетчеризации;
  проверяемое поведение (гварды `#destroyed` и `_layoutGeneration` в
  `#buildHierarchy`) сохранено и теперь реально проверяется.
- **React-тест** перехватывал `map.remove`, хотя биндинг зовёт `destroy()`. Перехват
  переведён на `destroy()` — реальную точку разрушения, — а наличие `remove()` как
  алиаса проверяется отдельным утверждением.

Общая закономерность: `85ff597` провёл переименование словаря стилей и удалил
`Map.remove()`, не обновив ни CHANGELOG, ни документацию, ни тесты. Отсюда и
рекомендация п. 14 — включить покрытие и линтер: половина этих расхождений
поймалась бы автоматически.

2. Добавить бюджеты для `orihon.react.esm.js` и `orihon.global.js`; поднять запас у Standard (находка 1).

8. Общий `mergeOptions`, отбрасывающий `undefined`, во всех 40 файлах (находка 8).
9. Refcount или явный release для разделяемого worker-пула (находка 9).
10. React: документировать требования к стабильности пропсов и предупреждать в dev о молча игнорируемых изменениях (находки 10, 11).
11. Единый контракт после `destroy()` через `assertAlive()` по образцу `ObjectManager` (находка 12).

**Постоянно (P2):**
