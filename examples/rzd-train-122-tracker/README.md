# РЖД 121В/122В — OSM route relation + автоматическая фактическая задержка РЖД

Эта версия основана на приложенном проекте и сохраняет его маршрут по OSM relation 17137928.

## Что добавлено

- `/api/rzd-actual?date=YYYY-MM-DD&train=121В`;
- backend-поллинг официальных веб-источников «Фактическое движение поездов» РЖД;
- автоматическое определение последней станции, для которой удалось распознать фактическое время/отклонение;
- автоматическая установка `delayMinutes` по этой станции;
- обновление раз в 60 секунд;
- статус `РЖД: LIVE / NO DATA / ERROR` в интерфейсе;
- фактические отклонения отображаются рядом с остановками;
- ручная корректировка сохранена и при её использовании автоматически выключает `Авто РЖД`;
- кнопка `Авто РЖД: ВКЛ/ВЫКЛ` и ручное `Обновить факт`.

## Важное ограничение

РЖД предоставляет пользователю сервис фактического движения, но публичной стабильной API-спецификации для этого сервиса нет. Поэтому backend использует адаптер к веб-источникам и эвристический парсер. Если внутренний формат РЖД изменится, приложение покажет `NO DATA` и продолжит работу по расписанию вместо выдачи выдуманной задержки.

## Проверка фактического API

Для рейса 16 августа 2026:

```text
http://127.0.0.1:8788/api/rzd-actual?date=2026-08-16&train=121В&force=1
```

Поле `latest` — последняя подтверждённая станционная отметка, `delayMinutes` — задержка, применяемая к движению поезда.

## Если РЖД поменяет endpoint

Можно без правки кода указать URL-шаблон через переменную окружения:

Windows PowerShell:

```powershell
$env:RZD_ACTUAL_URL='https://example/path?date={dateDot}&train={train}'
node server.mjs
```

Поддерживаемые placeholders:

- `{date}` → `2026-08-16`
- `{dateDot}` → `16.08.2026`
- `{train}` → `121В`

## Диагностика парсера

Для локального JSON/HTML fixture:

```powershell
$env:RZD_ACTUAL_FIXTURE='C:\path\actual.json'
node server.mjs
```

Это позволяет проверить парсер без внешнего запроса.


## RZD actual movement v2

В этой версии исправлен главный недостаток первого адаптера: запрос только
`date + train` открывал форму поиска, но не конкретный рейс.

Теперь backend делает:

1. Поиск полного маршрута Санкт-Петербург-Главн. (`2004000`) →
   Новороссийск (`2064110`).
2. Из ответа извлекает `ocrv_train_id`.
3. Открывает детальный слой фактического движения `layer_id=5381`.
4. Разбирает фактические времена по строкам станций.
5. Если РЖД отдаёт фактическое время без готового `+N мин`, задержка
   вычисляется сравнением с расписанием приложения.

### Диагностика

Если UI всё ещё показывает `NO DATA`, откройте:

```text
http://127.0.0.1:8788/api/rzd-actual?date=2026-08-16&train=121В&force=1&debug=1
```

Смотрите `attempts`:

- `phase: "search"` — поиск конкретного рейса;
- `detailIds` — найденные `ocrv_train_id`;
- `phase: "detail"` — загрузка фактического движения рейса;
- `observations` — сколько станционных отметок распознано;
- `preview` — короткий текст ответа РЖД для диагностики.

URL РЖД недокументированы и могут меняться, поэтому fallback на расписание
остаётся обязательным.
